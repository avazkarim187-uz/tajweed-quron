# Full platform rewrite from native Android to Expo (React Native/TypeScript)

The entire Android app (Kotlin/Jetpack Compose, Room, Hilt, Firebase) was deleted and replaced with an Expo SDK 51 app using expo-router for file-based navigation, expo-av for recording, AsyncStorage for persistence, and the same OpenAI Whisper integration for speech-to-text. The new app preserves the same feature set — 12 tajweed rules, 7 surahs with 35 ayahs, voice recording with Whisper transcription, Levenshtein-based scoring, progress tracking — but drops Firebase auth/sync entirely, simplifying to a local-only app. All UI text remains in Uzbek.

**Watch for:** The API key is stored in plaintext AsyncStorage with no encryption (confirmed). The home screen displays hardcoded stats (`completedRules = 3`, `overallScore = 72`, `streakDays = 5`) instead of reading from the ProgressContext (confirmed). The feedback screen (`feedback/[id].tsx`) renders entirely hardcoded mock data and never receives or displays actual analysis results (confirmed). The practice list screen always shows `score = 0` and `attempts = 0` — it never queries the ProgressContext (confirmed). The `RecordingContext` is instantiated at the root layout but never used by any screen; all recording logic is duplicated locally in each screen that records (confirmed).

## High-level view

The app uses expo-router's file-based navigation with a tab layout (5 tabs: Home, Lessons, Quran, Practice, Progress) and stack screens for detail views. Three React contexts wrap the app: ThemeContext (light/dark/system persistence), ProgressContext (score tracking with AsyncStorage), and RecordingContext (audio session management). However, RecordingContext is dead code — the practice and recording screens both manage their own audio sessions independently, duplicating permission requests, recording lifecycle, and error handling.

The Whisper integration is straightforward: record audio via expo-av, POST as multipart form data to the OpenAI transcriptions endpoint with the user-provided API key, then compare the transcription against expected Arabic text using Levenshtein distance. The scoring approach strips diacritical marks before comparison, meaning it cannot actually evaluate tajweed rule compliance — it measures consonant-level pronunciation accuracy, not rule-specific application.

The data layer hardcodes all content as TypeScript arrays (no database). Progress persists to AsyncStorage as a JSON blob. The pattern of calling `saveProgress` inside `setProgress`'s updater function means each state update triggers an async write, but because the updater captures a stale closure over the state, concurrent rapid updates could race, though in practice users can't trigger fast enough for this to matter.

The home screen, practice list, and feedback screen all display hardcoded values rather than reading from the progress system, making three of the app's screens non-functional in terms of reflecting actual user activity.

<summary>Issues (7)</summary>

1. **API key stored in plaintext AsyncStorage** — AsyncStorage is unencrypted on both platforms. Use `expo-secure-store` (already compatible with this Expo SDK version) to store the API key.
2. **Home screen stats are hardcoded** — `completedRules = 3`, `overallScore = 72`, `streakDays = 5` are constant literals. Wire them to `useProgress()` to display actual data.
3. **Feedback screen is fully mocked** — `feedback/[id].tsx` displays hardcoded Bismillah text and a fixed score of 78. It never receives route params containing the actual analysis result. Either pass results via params/context or remove the screen.
4. **Practice list ignores ProgressContext** — `app/(tabs)/practice.tsx` hardcodes `score = 0` and `attempts = 0` for every rule instead of calling `getProgressForRule()`.
5. **RecordingContext is dead code** — Instantiated in `_layout.tsx` but never consumed by any screen. The practice screen and recording screen each implement their own recording logic. Either use the context or remove it.
6. **Tab bar ignores theme** — `_layout.tsx` and `(tabs)/_layout.tsx` hardcode `#1B5E20` header colors and `#757575` inactive tint. When dark mode is active, these colors don't adapt; the header is correct by coincidence (dark green works on dark backgrounds) but the tab bar inactive color is wrong on dark surfaces.
7. **Word-level error comparison is misleading** — `analyzeRecitation` splits normalized text on spaces and compares word-by-word positionally. A single inserted or deleted word shifts all subsequent positions, cascading false positives for the remainder of the ayah.

## Plaintext API key in AsyncStorage

The `storage.ts` service stores the OpenAI API key directly:

```typescript
export async function saveApiKey(key: string): Promise<void> {
  await AsyncStorage.setItem(StorageKeys.API_KEY, key);
}
```

AsyncStorage on Android writes to an SQLite database in the app's data directory, readable on rooted devices or via adb backup. On iOS it's in the app sandbox (less exposed but still unencrypted). Expo provides `expo-secure-store` which uses the Android Keystore and iOS Keychain — it's a drop-in replacement for storing a single string value like an API key.

## Home screen disconnected from progress system

The home screen imports `useTheme` but not `useProgress`. The stats section renders constants:

```typescript
const completedRules = 3;
const overallScore = 72;
const streakDays = 5;
```

The ProgressContext already exposes `getMasteredRulesCount()`, `getOverallScore()`, and `getStreak()`. These need to be wired in. Similarly, the "So'nggi natijalar" section always displays "Hozircha natijalar yo'q" with no code path to show actual recent results.

## Feedback screen renders mock data

`app/feedback/[id].tsx` accepts an `id` route parameter but ignores it entirely. It displays:

```typescript
const mockScore = 78;
const originalText = '...bismillah...';
const transcribedText = '...';
```

No code retrieves a recording result by ID from storage or context. The screen is effectively a static mockup. The practice session screen (`app/practice/[ruleId].tsx`) shows results inline and never navigates to this feedback screen, making it an orphaned route.

## RecordingContext unused

The root `_layout.tsx` wraps the entire app in `<RecordingProvider>`, which initializes state, loads recording history from AsyncStorage, and exposes `startSession`, `stopSession`, and `saveResult`. None of these are called anywhere. Both `app/recording.tsx` and `app/practice/[ruleId].tsx` import `audioRecorder` directly and manage their own recording refs, permission checks, and error state. The duplicated logic between these two screens is nearly identical — 40+ lines of recording management code repeated.

## Tajweed analysis doesn't analyze tajweed

The `tajweedAnalyzer.ts` normalizes both expected and transcribed text by stripping all diacritical marks (harakat), then runs Levenshtein distance on the stripped consonant skeleton:

```typescript
export function normalizeArabic(text: string): string {
  return text
    .replace(/[\u0610-\u061A\u064B-\u065F\u0670...]/g, '')
    .replace(/\s+/g, ' ')
    .trim();
}
```

Since tajweed rules are entirely about *how* diacritical marks, nasalization, prolongation, and assimilation are applied, stripping them before comparison means the scoring cannot distinguish between correct tajweed application and incorrect tajweed application. Two recitations with identical consonants but completely different harakat produce the same score. The word-level error list then reports positional word mismatches that don't correspond to tajweed errors.

For a pronunciation accuracy tool (did the user say roughly the right words?) this works. For a tajweed assessment tool (did they apply ghunna, madd, ikhfa correctly?) it does not. The app's description claims tajweed analysis.

## Practice list doesn't reflect progress

`app/(tabs)/practice.tsx` renders each rule with:

```typescript
const score = 0;
const attempts = 0;
```

These are local constants, not derived from the ProgressContext. The screen imports nothing from `useProgress`. After a user completes practice sessions and achieves scores, the practice list still shows 0% and 0 attempts for every rule.

## Tab layout colors don't respond to theme

Both `_layout.tsx` and `(tabs)/_layout.tsx` use inline color literals for navigation chrome:

```typescript
headerStyle: { backgroundColor: '#1B5E20' },
headerTintColor: '#FFFFFF',
tabBarActiveTintColor: '#1B5E20',
tabBarInactiveTintColor: '#757575',
```

The ThemeContext is available but not consumed here. In dark mode, `#757575` (medium gray) for inactive tabs against a dark background provides insufficient contrast. The proper fix is reading theme colors from context, but since expo-router's layout components render before context is available in the tree, this requires either lifting theme resolution outside the router or using a wrapper pattern.
