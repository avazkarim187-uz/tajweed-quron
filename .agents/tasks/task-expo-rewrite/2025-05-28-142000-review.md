# Expo rewrite — v2 review (post-fix pass)

Five of the seven v1 issues have been addressed: the home screen now pulls live stats from ProgressContext, the practice list calls `getProgressForRule` for each rule, RecordingContext is removed, the feedback screen loads actual recording results by ID from storage, and the API key is stored via `expo-secure-store`. The two acknowledged items (tab bar dark-mode colors and word-level error cascading) remain unchanged with a clarifying comment added to the analyzer.

**Watch for:** The streak calculation has an off-by-one in its day-boundary logic that inflates the count (confirmed). The `clearAll` function doesn't reset in-memory ProgressContext state, so the UI continues showing stale data until app restart (confirmed).

**Verdict**: APPROVED

## High-level view

The data flow from recording through analysis to feedback is now connected end-to-end. A user records audio in `practice/[ruleId].tsx`, gets a `RecordingResult` with `id = Date.now()`, which is persisted to AsyncStorage and navigated to via `/feedback/{id}`. The feedback screen retrieves the full results array and finds the matching entry. The home screen and practice list both consume the same ProgressContext, so scores and attempt counts reflect reality.

The streak counter in ProgressContext uses overlapping day windows (`dayStart - dayMs` as the lower bound instead of `dayStart`), meaning a single practice session can count toward two consecutive "streak days." The practical impact is mild — streaks will read 1 higher than expected — but it contradicts user expectations for what "days in a row" means.

The settings screen's "clear all data" calls `clearAll()` which wipes AsyncStorage and SecureStore, but doesn't call any ProgressContext setter. The in-memory `progress` array remains populated until the next app launch triggers `loadProgress()` from the now-empty storage.

## Streak calculation day-boundary overlap

In `ProgressContext.tsx`, the streak loop:

```typescript
for (let i = 0; i < 365; i++) {
  const dayStart = now - i * dayMs;
  const dayEnd = dayStart + dayMs;
  const hasActivity = progress.some(
    (p) => p.lastPracticeDate >= dayStart - dayMs && p.lastPracticeDate < dayEnd
  );
```

For iteration `i=0` (today), `dayStart = now` and the check is `>= now - dayMs` (yesterday) to `< now + dayMs` (tomorrow). For `i=1` (yesterday), the window is `>= now - 2*dayMs` to `< now`. The windows overlap: activity at `now - 0.5*dayMs` satisfies both `i=0` and `i=1`. The lower bound should be `dayStart`, not `dayStart - dayMs`. Additionally, using `Date.now()` as the anchor without normalizing to midnight means the "today" window shifts with time-of-day, so a user practicing at 11pm and then 1am the next calendar day might not see their streak continue because the relative window has moved.

## State/storage desync on clear

`app/settings.tsx` calls `clearAll()` which removes all AsyncStorage keys and deletes the SecureStore API key entry. But the ProgressProvider's `progress` state still holds the array loaded at mount time. The home screen will continue displaying the old `completedRules`, `overallScore`, and `streakDays` until the component tree remounts (typically requiring an app restart or navigation reset). The fix is either to expose `setProgress([])` as a `resetProgress` method on the context, or to trigger a full navigation reset after clearing.
