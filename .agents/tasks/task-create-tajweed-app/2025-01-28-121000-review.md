# Bug-fix pass for 8 critical issues (v2)

The fix commit addresses all 8 issues from the first review: API key reads from EncryptedSharedPreferences on every request via an interceptor closure, the score display no longer double-multiplies, the theme preference propagates from SharedPreferences through a listener into Compose state, audio files are cleaned on app start and after transcription, Firestore sync uses `.first()` instead of indefinite collect and pulls on login, the TajweedAnalyzer now uses Levenshtein alignment with rule-aware error attribution, Room Converters use Gson JSON, and the API key is stored encrypted.

**Watch for:** Remote progress pull uses `OnConflictStrategy.REPLACE` with `id = 0`, which will insert new rows rather than merging by `ruleId` (likely). SharedPreference listener in `MainActivity` is never unregistered, risking garbage collection of the listener and a minor lifecycle hygiene issue (confirmed). `SettingsViewModel` creates its own `EncryptedSharedPreferences` instance independently from Hilt, bypassing the DI graph (confirmed).

## High-level view

The API key interceptor captures the `encryptedPrefs` reference (not the key value) and calls `getString` on every request. The encrypted prefs are provided via Hilt with a custom `@EncryptedPrefs` qualifier — but `SettingsViewModel` creates a second instance manually rather than injecting it, duplicating initialization and creating a maintenance fragility.

Theme propagation uses a `mutableStateOf` field in `MainActivity` with an `OnSharedPreferenceChangeListener` that reacts to settings changes. The listener is never unregistered, and because it's an anonymous lambda with no external strong reference, it may be garbage-collected on devices where `SharedPreferencesImpl` uses a `WeakHashMap` internally.

The Levenshtein-based analyzer handles insertions and deletions without cascading positional errors, and maps mismatches to rule-specific error names when the involved character belongs to a rule's letter set. The heuristic doesn't check character context (e.g., a ب error is attributed to Iqlob even if not preceded by nun), so it over-attributes rather than under-attributes.

The Firestore pull strategy unconditionally inserts remote progress on login. Since `UserProgress` has an auto-generated `id` as its primary key, inserting remote records with `id = 0` creates new rows rather than updating existing ones for the same `ruleId`, accumulating duplicates across logins.

## Progress pull overwrites vs. duplicates

`AuthViewModel.pullRemoteProgress` fetches remote `UserProgress` objects from Firestore and passes them through `progressRepository.updateProgress(remote)`, which calls `userProgressDao.insertOrUpdate(progress)`:

```kotlin
@Insert(onConflict = OnConflictStrategy.REPLACE)
suspend fun insertOrUpdate(progress: UserProgress)
```

The `UserProgress` entity uses `@PrimaryKey(autoGenerate = true) val id: Int = 0`. Remote objects constructed in `getRemoteProgress` don't set `id`, so they arrive with `id = 0`. Room's auto-generate behavior treats 0 as "generate a new ID," inserting a fresh row every time rather than replacing the existing row for that `ruleId`. After multiple logins, the `user_progress` table accumulates duplicate entries per rule, and queries like `getProgressByRule(ruleId)` return one of potentially many rows.

The fix is either to make `ruleId` the primary key (it's already unique per rule by design) or to add a DAO method that queries by `ruleId` first and updates the existing row's fields.

## SharedPreference listener lifecycle

```kotlin
prefs.registerOnSharedPreferenceChangeListener { sharedPreferences, key ->
    if (key == "theme") { ... }
}
```

The anonymous lambda captures `this` (the Activity). The stock `SharedPreferencesImpl` uses a `WeakHashMap<OnSharedPreferenceChangeListener, Object>` — because the lambda has no external strong reference, it can be garbage-collected at any time, causing the theme to stop updating after GC runs. The correct pattern is to store the listener as a class field (ensuring a strong reference) and unregister in `onDestroy`.

## Duplicate EncryptedSharedPreferences in SettingsViewModel

`AppModule` provides `EncryptedSharedPreferences` as a Hilt singleton with `@EncryptedPrefs`. But `SettingsViewModel` creates its own instance:

```kotlin
private val encryptedPrefs: SharedPreferences by lazy {
    val masterKeyAlias = MasterKeys.getOrCreate(MasterKeys.AES256_GCM_SPEC)
    EncryptedSharedPreferences.create("tajweed_secure_prefs", ...)
}
```

Both target the same file. Writes from `SettingsViewModel.saveApiKey()` and reads from the OkHttp interceptor go through different instances. Since EncryptedSharedPreferences reads from disk on each access, correctness is maintained today. But the file name `"tajweed_secure_prefs"` is now a string constant duplicated in two locations with no shared reference — a classic drift risk. Injecting `@EncryptedPrefs` would eliminate both the duplication and the redundant `MasterKeys` initialization.

## Levenshtein analyzer rule attribution

The rule-attribution heuristic maps errors to rules based on whether the expected or actual character appears in that rule's letter set. It doesn't check context — a ب error is attributed to "Iqlob" whenever rule 4 is in `ruleIds`, even if the ب isn't preceded by a nun sakinah. For a learning app that surfaces rule names as study hints, this over-attribution is acceptable, but users may see misleading rule names on errors that have nothing to do with the named rule.

The `totalOperations` variable is incremented in the loop but never used anywhere. It should be removed.
