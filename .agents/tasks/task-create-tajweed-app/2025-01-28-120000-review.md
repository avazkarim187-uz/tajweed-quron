# AI Tajweed Ustoz: Greenfield Android app for Quran recitation with AI analysis

A complete Android application for teaching tajweed (Quran recitation rules) using AI-powered speech recognition. The app provides 12 tajweed rules with Arabic examples and Uzbek explanations, 35 Quran ayahs across 7 surahs, voice recording via MediaRecorder, transcription via OpenAI Whisper, character-level comparison for scoring, Firebase auth and sync, and a 13-screen Compose UI with Material3 theming. The architecture follows standard Android conventions: Room for persistence, Hilt for DI, repository pattern, ViewModel per screen.

**Watch for:** The OpenAI API key is stored in plaintext SharedPreferences (confirmed). The `TajweedAnalyzer` performs naive character-by-character comparison of Arabic text against Whisper transcription output, meaning the "tajweed analysis" doesn't actually analyze tajweed rules — it's a string diff (confirmed). The `AppModule.getApiKey()` always returns empty string, so the OkHttp interceptor sends `Bearer ` with no token while settings stores the key elsewhere (confirmed). Audio recording files in cache are never cleaned up (confirmed).

## High-level view

The application is structured as a single-activity Compose app with Hilt injection, a Room database seeded on first launch via `DatabaseCallback`, and 13 navigation destinations. The data layer cleanly separates DAOs, repositories (interface + impl), and remote services. The Whisper integration sends recorded audio to OpenAI for transcription, then the `TajweedAnalyzer` compares the transcription character-by-character against expected text to produce a score. This comparison has no awareness of actual tajweed rules — it cannot distinguish between a pronunciation error in ghunna versus a simple missed letter.

The API key management has a structural disconnect: `SettingsViewModel` saves the key to SharedPreferences and reads it back, but `AppModule` provides the OkHttp client at DI graph creation time with a hardcoded `getApiKey()` that returns empty string. The interceptor never consults SharedPreferences, so the user-configured key is never used for API calls.

Firebase authentication is fully wired through `FirebaseService` with email/password and Google sign-in, and Firestore sync pushes local progress. However, there's no pull-merge strategy — `syncProgress()` only pushes, and `getRemoteProgress()` exists but is never called from any ViewModel or repository.

The theme supports light, dark, and system modes with dynamic color on Android 12+, but the `SettingsViewModel`'s theme preference never feeds back into `TajweedUstodTheme` — the composable only reads `isSystemInDarkTheme()` and ignores the stored preference.

1. **API key never reaches OkHttp** — `AppModule.getApiKey()` returns empty string; the key saved in SharedPreferences by `SettingsViewModel` is never read by the interceptor. Wire the interceptor to read from SharedPreferences or inject the key dynamically.
2. **TajweedAnalyzer is a character diff, not tajweed analysis** — It compares Arabic characters positionally without understanding harakat, madd, ghunna, or any rule. 3. **API key stored in plaintext SharedPreferences** — Use `EncryptedSharedPreferences` from the AndroidX Security library.
4. **Audio files in cache never deleted** — `outputFile` paths accumulate in `cacheDir` indefinitely. Add cleanup after successful upload or on app start.
5. **Theme preference not applied** — `TajweedUstodTheme` ignores the `ThemeMode` stored in SharedPreferences; the user's dark/light selection has no effect.
6. **Firestore sync is push-only** — `getRemoteProgress()` exists but is never called. Multi-device users will lose data on new installs.
7. **Converters for List<String> break on values containing commas** — Arabic text with commas will be corrupted by `joinToString(",")` / `split(",")`. Use JSON serialization.
8. **Score display inconsistency** — `TajweedAnalyzer` produces scores 0-100, but `HomeScreen` displays `(overallScore * 100).toInt()%` treating it as 0-1, resulting in inflated percentages.

## API key lifecycle disconnect

The `AppModule` creates a singleton `OkHttpClient` with an interceptor that calls `getApiKey()`, a private function returning empty string:

```kotlin
private fun getApiKey(): String {
    // API key should be stored securely, e.g., in BuildConfig or encrypted preferences
    return ""
}
```

Meanwhile, `SettingsViewModel.saveApiKey()` writes to SharedPreferences under key `"api_key"`. Since the OkHttp client is a Hilt singleton created at app launch, even if `getApiKey()` were modified to read SharedPreferences, it would only read the value once. The interceptor captures the result of `getApiKey()` in a closure, not a live reference. The fix requires either (a) the interceptor reading SharedPreferences on every request, or (b) recreating the client when the key changes. Option (a) is simpler for a learning app.

## TajweedAnalyzer limitations

The analyzer's core logic:

```kotlin
for (i in 0 until minLength) {
    if (expectedChars[i] == actualChars[i]) {
        matchCount++
    } else {
        errors.add(...)
    }
}
```

This is positional character comparison. Whisper's Arabic transcription output may differ in diacritical marks (harakat), whitespace, hamza forms, or transliteration style from the stored `arabicText`. A single inserted or deleted character shifts all subsequent positions, cascading into 100% error rate for the remainder. The `ruleIds` parameter is accepted but never used in the analysis logic — no rule-specific checking occurs.

For an MVP this is functional as a rough pronunciation match, but the app's marketing premise ("AI-powered tajweed analysis with color-coded feedback") overstates what this delivers.

## Plaintext API key storage

`SettingsViewModel` stores the OpenAI API key in standard SharedPreferences:

```kotlin
prefs.edit().putString("api_key", key).apply()
```

On rooted devices or via backup extraction, this key is trivially readable. The AndroidX Security library provides `EncryptedSharedPreferences` as a drop-in replacement with hardware-backed encryption.

## Audio file accumulation

`RecordingViewModel.startRecording()` creates a new file in `cacheDir` each session:

```kotlin
val file = File(context.cacheDir, "recording_${System.currentTimeMillis()}.m4a")
```

These files are never deleted after the transcription completes. The `RecordingResult` entity stores the `audioPath`, but nothing reads it back for playback, and nothing purges old recordings. Over time this will consume significant storage, particularly on devices with limited internal space.

## Theme preference has no effect

`TajweedUstodTheme` accepts a `darkTheme: Boolean` parameter defaulting to `isSystemInDarkTheme()`. The `MainActivity` calls `TajweedUstodTheme { ... }` without passing the user's stored preference. The `SettingsViewModel` writes the theme to SharedPreferences but no composable reads it to control the theme at the root. The user can toggle the setting, see it reflected in the dropdown, but the actual color scheme never changes.

## Firestore sync gap

`FirebaseService` has both `syncProgress()` (push) and `getRemoteProgress()` (pull). `SettingsViewModel.syncProgress()` only calls the push path:

```kotlin
fun syncProgress() {
    viewModelScope.launch {
        val user = firebaseService.getCurrentUser() ?: return@launch
        progressRepository.getProgress().collect { progressList ->
            firebaseService.syncProgress(user.uid, progressList)
        }
    }
}
```

The `collect` here is problematic: it subscribes to the Flow indefinitely, meaning every local progress change triggers a Firestore write for the entire progress list. This is both wasteful and unbounded — the coroutine never cancels unless the ViewModel is cleared.

## Room TypeConverter fragility

The `Converters.listToString` uses comma-joining:

```kotlin
fun listToString(list: List<String>?): String? {
    return list?.joinToString(",")
}
```

While currently no entity uses `List<String>` columns directly (the `tajweedRuleIds` and `lettersList` are plain `String` fields), the converter is registered database-wide. If any future field uses it with values containing commas (common in Arabic text with diacritics), data corruption will occur silently.

## Score scale mismatch

`TajweedAnalyzer.analyzeTranscription()` returns a score from 0 to 100:

```kotlin
val score = if (maxLength > 0) {
    (matchCount.toFloat() / maxLength.toFloat()) * 100f
} else { 0f }
```

But `HomeScreen.DailyStatsCard` displays:

```kotlin
Text(text = "${(overallScore * 100).toInt()}%")
```

Since `overallScore` is already the average of `practiceScore` values (which are 0-100), multiplying by 100 again yields values like "7000%" for a 70% score. The same pattern appears in `RecentResultItem`.
